# 14 — A model call behind a queue

What an AceMQ AI adapter does when the downstream a handler calls is a
language model. The rule is that a model call behaves like any other
unreliable downstream: bounded concurrency, retries in the broker, a
dead-letter queue, idempotency, back-pressure and metrics. The adapter
guarantees delivery semantics, not answer semantics.

Today one library implements this area, `acemq-java-amqp-ai` (on
`acemq-java-amqp`). The cases live in `cases/pending/` and run with
`--pending --only AI`: they are not part of the default run, because a
messaging library without an AI adapter has nothing to answer them with.
A second adapter (Python first, by the scope's port order) runs the same
cases through its own driver.

No case calls a real model. The runner plays the model itself — a scripted
server on loopback speaking Ollama's `POST /api/chat` and the OpenAI-compatible
`POST /v1/chat/completions` — so a case is deterministic and needs no GPU and
no key. The driver op is `aiConsume` ([driver contract](../docs/driver-contract.md#ai-adapters)).

Classification of what the model answered:

| The model | Retryable | Outcome |
|---|---|---|
| answers | — | `answered` |
| HTTP 429, with or without `retry-after` | yes, and the consumer pauses | `failed` |
| HTTP 5xx, Anthropic 529, connection refused | yes | `failed` |
| no answer within the call's timeout | yes | `timed_out` |
| HTTP 400, context too long, authentication | no: `{queue}.dlq` | `failed` |
| a refusal or content filter | no: `{queue}.dlq` | `refused` |

### AMQP-AI-001 (MUST) An answered call is counted in tokens

Cases: AI-001

One message is one model call. The adapter reports a
`acemq.ai.request.duration` timer with tags `queue`, `provider`, `model` and
`outcome` `answered`, and an `acemq.ai.tokens` counter per `kind` (`input`,
`output`, `cached_input`) whose values are the token counts the model
reported for that call. Prompts and replies are never put in a metric, a
span or a log by default: they are customer data.

### AMQP-AI-002 (MUST) A rate limit pauses the consumer and takes a retry rung

Cases: AI-002

A rate-limited call (HTTP 429) pauses the consumer — no deliveries
(`basic.cancel`) — for at least the `retry-after` the model gave, or a
jittered default when it gave none, and fails the message as retryable so it
takes the retry ladder. The pause does the waiting; nothing sleeps in the
consumer thread. The next call for that message comes no sooner than
`retry-after` after the refused one, and nothing is lost or dead-lettered.

### AMQP-AI-003 (MUST) A call with no answer in time is retryable

Cases: AI-003

A call that gets no answer within its timeout is reported with outcome
`timed_out` and is retryable: the message takes the retry ladder and is asked
again.

### AMQP-AI-004 (MUST) A bad request goes to the dead-letter queue at once

Cases: AI-004

A call the model rejects as a bad request (HTTP 400, a context that is too
long, an authentication failure) cannot succeed when repeated, so the message
goes to `{queue}.dlq` after that one call, whatever the retry policy, with
`x-acemq-error` saying why.

### AMQP-AI-005 (MUST) A refusal goes to the dead-letter queue as refused

Cases: AI-005

A reply the model ended as a refusal (a content filter, `stop_reason: refusal`)
is deterministic for the same input, so by default it is not retried: the
outcome is `refused` and the message goes to `{queue}.dlq` with an
`x-acemq-error` that says it was refused. A fallback model, asked once, is
opt-in.

### AMQP-AI-006 (MUST) A redelivery after an answered call is not billed again

Cases: AI-006

With the idempotent consumer, a message whose model call already answered is
not sent to the model again when the broker redelivers it — for example
because the connection was lost after the answer and before the
acknowledgement. The model sees exactly one call.

### AMQP-AI-007 (MUST) An exhausted token budget pauses, a refilled one resumes

Cases: AI-007

A token budget is a watermark, not a per-message denial. When what is left in
the budget's window falls below what the messages that could be in flight
might spend (`prefetch × maxOutputTokens`), every consumer sharing it pauses;
when the window refills they resume by themselves, and every message is
handled. A message already in flight always finishes, so the most a window
overspends is that reservation.
